## 1. 設計の原則

次の原則を、すべての実装に適用する。

1. **低結合・高凝集**: 責務ごとに、モジュールを分ける。1 つのモジュールは、1 つの責務を持つ。
2. **明示的な契約**: モジュールどうしは、公開した型・関数（契約）だけでつなぐ。相手の内部構造や、暗黙の前提に頼らない。
3. **データの所有者を 1 つに**: どのデータも、所有者（更新できる唯一のモジュール）を決める。他は、読むだけ。
4. **同じ知識を 1 か所に**: ルール、駒の定義、プロトコルの型、設定は、それぞれ 1 か所にだけ書き、他は、そこから生成・参照する。
5. **単純さ**: 過度な条件分岐、重複、早すぎる抽象化を避ける。駒ごとの `if` を作らず、データで表す。
6. **実装の前に、既存を確認**: 既にある実装・拡張点を確認し、共通の処理は再利用してから、新しく作る。

## 2. 技術選定

| 領域 | 選定 | 理由 |
| --- | --- | --- |
| ルール・AI・サーバー | Rust | 高速化が必要（特に AI）。型で不正な状態を防ぐ |
| サーバーの枠組み | axum（Tokio 上）、WebSocket | 軽量で、Rust の非同期処理と相性がよい |
| データベース | SQLite | 単一ファイルで、ローカルに向く |
| フロントエンド | TypeScript + Vite | ビルドが速く、TypeScript・wasm・three.js を扱いやすい |
| 3D 描画 | three.js | 実績が多く、ブラウザの 3D に十分 |
| 高速化が必要なフロント処理 | Rust を wasm にして使う | 移動範囲・危険判定を、ルールと同じコードで動かす |
| 型の共有 | Rust の型から TypeScript の型を生成 | プロトコルの型を 1 か所に（原則 4） |

## 3. リポジトリの構成

```
nandemo-shogi/
├── Cargo.toml              # Rust のワークスペース
├── crates/
│   ├── rules/              # ゲームルール（純粋な計算）
│   ├── ai/                 # AI
│   ├── protocol/           # 通信メッセージの型（TypeScript の型を生成する元）
│   ├── server/             # axum サーバー、ルーム、マッチング、保存
│   └── rules-wasm/         # rules を wasm にして、ブラウザから使う入口
├── data/
│   └── pieces.toml         # 駒のデータ（唯一の定義）
├── web/                    # フロントエンド（Vite + TypeScript）
│   └── src/
│       ├── net/            # WebSocket の接続、メッセージの送受信
│       ├── store/          # クライアントの状態（サーバーの状態の写し）
│       ├── rules-bridge/   # wasm の呼び出しの窓口
│       ├── scene/          # three.js の 3D 表示
│       ├── ui/             # 自作の UI 部品と画面
│       └── tokens/         # デザイントークン
├── docs/                   # 仕様書など
└── scripts/                # 開発用スクリプト、フック
```

## 4. モジュールの責務と契約

### 4.1 `rules`（ゲームルール）

- **責務**: [game-rules.md](game-rules.md) を、そのまま実装する。盤・駒・状態の型、合法な行動の列挙、行動の適用、危険な駒の判定、勝敗の判定。
- **契約**:
  - `GameState` を受け取り、`Action` を適用して、新しい状態と `Event` の列を返す。
  - 状態は、不変条件（R-04）を、型と検証で守る。不正な行動は、`Err` で返す。
  - `legal_moves(state, piece)`、`threatened_pieces(state)` などの、読み取りの関数を公開する。
- **依存しない**: 入出力、ネットワーク、時刻、乱数の発生源。ドローは、乱数を引数（`&mut impl Rng`）で受け取る。
- **所有するデータ**: 駒のデータ（`data/pieces.toml` を、コンパイル時に埋め込んで読み込む）の解釈。

### 4.2 `ai`

- **責務**: 席の状態から、ドローの選択と行動を決める。[online.md](online.md) の 7 章。
- **契約**: `choose_pick(state, drawn, level, rng)`、`choose_action(state, level, deadline, rng)`。締め切りを守って返す。
- **依存**: `rules` だけ。サーバーのことは、知らない。

### 4.3 `protocol`

- **責務**: クライアント・サーバー間のメッセージの型の定義。TypeScript の型は、ここから生成する。
- **依存**: `rules` の型（`Action`、`Event` など）を、そのまま使う（重複して定義しない）。

### 4.4 `server`

- **責務**: 接続の管理、ルームとマッチング、タイマー、AI の呼び出し、記録の保存。
- **構造**: 1 ルーム = 1 つの Tokio タスク（アクター）。ルームの状態は、そのタスクだけが持ち、更新する。接続は、メッセージをルームへ送る。AI の計算は、専用のスレッドで行い、締め切りで打ち切る。
- **内部の分け方**:
  - `ws`: WebSocket の入口（オリジンの検証、接続の読み書き、メッセージの検証、頻度の制限）と、`hub`: 接続の管理、ロビーへの振り分け、結果の配送、時計と AI の駆動（通信の形に依存しない）
  - `lobby`: マッチングとルームの一覧・管理（プレイヤーとルームの対応、終わったルームの片付け）
  - `room`: ルームの状態、手番の進行、タイマー、切断の処理。時計（`Millis`）と乱数は、外から渡し、送るべきメッセージ（`Outbound`）を返す純粋な部分（通信と時計に依存しない。1 ルーム 1 タスクの実行は、通信の層が担う）
  - `record`: 終わった対局の記録（純粋なデータ）と、記録からの再現（`replay`）
  - `store`: SQLite への保存（**このモジュールだけが、DB に触れる**）。専用のスレッドで保存し、対局を止めない
- **依存**: `rules`、`ai`、`protocol`。

### 4.5 `rules-wasm`

- **責務**: `rules` の読み取りの関数（移動範囲、行動のプレビュー、危険判定）を、ブラウザから呼べる形で公開する。ルールを書き直さない（`rules` をそのまま使う）。
- **契約**: 状態は、サーバーが送る盤面の写し（`StateView`）の JSON。結果も JSON。状態を持たない（呼ぶたびに、写しから `GameState` を復元して、不変条件を検査する）。不正な入力は、例外（エラー）で返す。
- **公開する関数**: 駒の種類の定義、合法な行動、駒の移動先、駒の配置先（位置と向き）、行動のプレビュー（出来事と、その後の状態）、危険な駒。
- **制約**: 写しには、脱落の順がないので、復元した状態の脱落の順は近似（プレビューで、脱落が起きたときの順位は、目安）。盤の大きさは 64 まで。
- **依存**: `rules`、`protocol`（写しの型と復元）。

### 4.6 `web`（フロントエンド）

依存の向きは、上から下のみ。逆向きや、横断は禁止する。

```
ui（画面・部品） ──▶ store ──▶ net
        │              │
        └──────────────┴──▶ rules-bridge（wasm）
scene（3D）──▶ store（読み取りのみ）
```

- `net`: サーバーとの通信だけ。受信したメッセージを、`store` へ渡す。
- `store`: サーバーの状態の写しと、画面だけの状態（選択中の駒など）。サーバーの状態は、`net` 経由でだけ更新する（所有者はサーバー）。
- `rules-bridge`: wasm の呼び出しの窓口。ほかのモジュールは、wasm を直接呼ばない。
- `scene`: 状態から 3D を描く。状態を変えない。アニメーションは、`events` を受けて、順に再生する。
- `ui`: 画面と自作部品。`tokens` の値だけを使う。

## 5. データの所有者

| データ | 所有者（更新できる唯一の場所） | 他は |
| --- | --- | --- |
| 駒の定義（数値） | `data/pieces.toml` | `rules` が読み込む。`web` は、`rules-wasm` 経由で使う |
| 対局の状態 | サーバーのルーム（アクター） | クライアントは、写しを受け取って表示 |
| 通信メッセージの型 | `protocol` | TypeScript は、生成したものを使う |
| 対局の記録 | `server` の `store` | 読み取りは、`store` の関数を通す |
| デザインの値 | `web/src/tokens` | 部品が参照する |
| 設定（待ち受けアドレス、許可オリジン、上限値） | サーバーの設定ファイル／環境変数 | `server` が読み込む |

## 6. 設定

外部公開に備え、次を設定で変えられるようにする（初期値は、ローカル向け）。

| 項目 | 初期値 |
| --- | --- |
| 待ち受けアドレス | `127.0.0.1`（ローカルホストのみ） |
| 許可するオリジン | ローカルホストのみ（`Origin` ヘッダーがない接続も拒否する） |
| 同時接続数の上限 | 100（`NANDEMO_MAX_CONNECTIONS`） |
| AI の手を見せるまでの最低の間 | 1500 ミリ秒（`NANDEMO_AI_DELAY_MS`） |
| メッセージ頻度・メッセージサイズの上限 | [online.md](online.md) の 6.4（コードの定数） |
| データベースのファイル | 作業ディレクトリ内の SQLite ファイル |
| ログの出力 | 標準出力 |

## 7. 非機能要件

| 項目 | 要件 |
| --- | --- |
| 決定論 | 同じシード・同じ行動の列から、同じ結果になる（ルールと AI の乱数は、シードから決まる） |
| テスト | `rules` に単体テストを書く。全駒の移動範囲、ダメージ、捕食と持ち駒、成り、勝敗・引き分け・パス、大きい駒と盤の端を網羅する。テストは、[game-rules.md](game-rules.md) の R- 番号を参照する |
| 再現テスト | 記録された対局を、シードと行動から再生して、結果が一致することを確認する |
| AI の時間 | どの強さでも、持ち時間（20 秒）を超えないことを、テストで確認する |
| 性能 | 描画は、一般的な PC で 60fps を目標。操作の確定から画面への反映は、ローカルで 100 ミリ秒以内を目標 |
| 対応ブラウザ | Chrome・Safari・Firefox の最新版 |
| セキュリティ | サーバーが正。入力の検証、サイズ・頻度の制限、オリジンの検証。ローカル限定の待ち受け |
| ログ | 接続・ルーム・対局の開始と終了・拒否した操作を、ログに残す。個人情報は扱わない |
| 保守性 | 1 から 6 の原則。駒の追加は、データ定義とモデルファイルの追加だけで済む |

## 8. 開発の進め方（目安）

実装は、Issue 単位で進める（[.claude/rules/issue-driven.md](../../.claude/rules/issue-driven.md)）。依存の下流から、次の順に作る。

1. `rules` と `data/pieces.toml`（テストつき）
2. `ai`（強さ 1 → 2 → 3）
3. `protocol` と `server`（ルーム・マッチング・タイマー・保存）
4. `rules-wasm` と `web` の土台（`net`・`store`・`tokens`・自作部品）
5. `scene`（盤と駒の 3D、アニメーション）
6. 画面（タイトル〜結果）の組み立てと、仕上げ

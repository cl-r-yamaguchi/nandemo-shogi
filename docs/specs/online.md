# オンライン対戦の仕様

| 項目 | 内容 |
| --- | --- |
| 版 | 1.1 |
| 関連 | [game-rules.md](game-rules.md)、[ui.md](ui.md)、[architecture.md](architecture.md) |

## 1. 前提

- **公開範囲**: 当面は、外部に公開せず、ローカルホスト（`127.0.0.1`）だけで待ち受ける。同じ PC の、複数のブラウザ・複数のタブから、同時に接続して遊べる。
- **外部公開への備え**: 待ち受けアドレス・許可するオリジン・接続数などを設定で変えられるようにし、公開するときに、構造を変えずに、認証などを足せる作りにする（[architecture.md](architecture.md)）。
- **サーバーが正**: 状態は、サーバーだけが持ち、更新する。クライアントは、「操作の要求」を送り、結果を受け取って表示する（クライアントの計算は、表示の補助にすぎない）。
- **全情報の公開**: ドロー結果・持ち駒を含め、すべての状態を、全員に送る。

## 2. プレイヤーの識別

認証はない。

- タブを開いたとき、ランダムなプレイヤー ID（推測しにくい長さ）を発行し、そのタブの `sessionStorage` に保存する。**`localStorage` は使わない**（同じブラウザの複数タブが、同一人物になるため）。
- リロードしても、同じ ID で復帰する。タブを閉じると、その ID は、再接続できなくなる。
- 表示名は、初期値が「ゲスト」＋数字。タイトル画面で変更できる（1〜12 文字）。

## 3. ルールの設定（リクエスト）

遊ぶには、「ルール」を設定する。

| 項目 | 範囲 | 初期値 |
| --- | --- | --- |
| 人数（AI を含む合計） | 2〜4 | 4 |
| AI の強さ | 1〜3 | 2 |

項目は、今後増やせるようにする（設定は、名前と値の集まりとして扱い、マッチングは、すべての項目が一致するかで判定する）。

## 4. ルームとマッチング

### 4.1 マッチング

1. プレイヤーが、ルールを決めて「あそぶ」を押す。
2. サーバーは、そのルールと**すべての項目が一致**し、**待機中で、空きがある**ルームを探す。複数あれば、最も古いルームに入れる。
3. なければ、新しいルームを自動で作り、そこに入れる。

### 4.2 ルームの状態

```
待機 ──(満員になる / Go を押す)──▶ 対戦中 ──▶ 終了
  │
  └─ 誰もいなくなる / 10 分間開始されない ──▶ 破棄
```

- **待機**: メンバーが揃うのを待つ。人間のメンバーは、いつでも退出できる。待機画面には、席の状況（人間／空き）と、Go ボタンを出す。
- **開始**: 次のどちらかで始まる。
  - 人数が満員（人間だけで、設定の人数に達した）になる。自動で始まる。
  - ルームにいる誰かが **Go ボタン**を押す。人間が 1 人でも始められる。空き席は、AI で埋める（AI の強さは、ルールの設定どおり）。
- **対戦中**: 途中参加はできない。途中で抜けた人は、切断として扱う（5 章）。
- **終了**: 結果を全員に見せる。「もう一度」で、同じルールで、新しいマッチングを始める。
- **破棄**: 誰もいなくなったルーム、作ってから 10 分間開始されないルームは、サーバーが片付ける。

### 4.3 席順

席は、時計回りの順番（そのまま手番の順）。**AI と人間が、なるべく交互になる**ように決める。

1. 人間の並びを、ランダムに入れ替える。AI も、同様に（AI どうしは区別しない）。
2. 人数が多いほうの種類を、先頭にして、人間・AI を交互に並べる。少ないほうを使い切ったら、残りは、続けて並べる。
   - 例（4 人）: 人間 2・AI 2 → 人間, AI, 人間, AI。人間 1・AI 3 → AI, 人間, AI, AI。人間 3・AI 1 → 人間, AI, 人間, 人間。
3. 並べた席に、色とマークを順に割り当てる（[ui.md](ui.md) の 3.2）。
4. 最初の手番の席は、ランダム（[game-rules.md](game-rules.md) の R-11）。

## 5. 接続の管理

- **切断**: 接続が切れても、手番の持ち時間は止まらない。
- **再接続**: 同じタブから、同じプレイヤー ID で再接続すると、その席に戻れる。戻ると、その時点の全状態が、まとめて送られる。
- **AI の代行**: 切断から 30 秒たっても戻らないとき、その席を AI が代行する（強さは、ルールの設定どおり）。代行中に再接続したら、次の手番から本人に戻る。代行中の手は、ログに残す。
- **全員が切断**: 全員が切断して 60 秒たったら、ルームを終了し、結果は「中断」として記録する。

## 6. 通信プロトコル

WebSocket（JSON のテキストメッセージ）で通信する。メッセージの型は、Rust 側を正として、TypeScript 側の型を生成する（[architecture.md](architecture.md)）。

### 6.1 共通

- すべてのメッセージは `{ "v": <プロトコル版>, "type": "<種別>", ... }` の形。版が合わなければ、接続時に拒否する。
- サーバー時刻と、クライアントの時計のずれの影響を避けるため、時間は「残りミリ秒」で送る。クライアントは、受信した時点からの経過で、残り時間を表示する。
- クライアントからの操作には、**手番番号**を付ける。サーバーは、古い番号・二重送信・手番でないプレイヤーの操作を、拒否する。

### 6.2 クライアント → サーバー

| type | 内容 | 使う場面 |
| --- | --- | --- |
| `hello` | プレイヤー ID、表示名 | 接続直後、再接続 |
| `find_room` | ルール | あそぶ |
| `leave_room` | なし | 待機ルームの退出 |
| `start` | なし | Go ボタン |
| `pick` | 手番番号、引いた 4 枚のうちの番号（0〜3） | 選択 |
| `act` | 手番番号、行動（配置・移動・回転）、成りの選択 | 行動の確定 |
| `resign` | なし | 投了 |

`act` の行動の中身:

- 配置: `{ kind: "place", piece: <種類>, anchor: [x, y], facing: <向き> }`
- 移動: `{ kind: "move", piece_id: <盤上の駒の ID>, to_anchor: [x, y] }`（直進の駒は、行き先をサーバーが決めるので、`to_anchor` は、クライアントの予想として送り、一致しなければ拒否する）
- 回転: `{ kind: "rotate", piece_id: <ID>, facing: <向き> }`
- 成り: `promote: true | false`（R-63。捕食と成りが可能なときだけ適用）

### 6.3 サーバー → クライアント

| type | 内容 |
| --- | --- |
| `room_state` | ルームの状態（席、ルール、待機・対戦中の別） |
| `game_started` | 席順、色、最初の盤面（空）、乱数のシードは含めない |
| `turn_started` | 手番のプレイヤー、手番番号、フェーズ、ドローで引いた 4 枚、残りミリ秒 |
| `state` | 全状態のスナップショット（再接続時、画面の復元用） |
| `applied` | 行動の結果。出来事（`events`）のリスト |
| `rejected` | 操作の拒否と理由（コード＋日本語の文言） |
| `game_over` | 順位、勝者、終了理由 |
| `notice` | 切断・AI 代行・ルーム破棄などの通知 |

`applied` の出来事（`events`）の種類: `placed`（配置）、`moved`（移動）、`rotated`（回転）、`damaged`（駒、ダメージ、残り HP）、`captured`（捕食された駒、行き先）、`promoted`（成り）、`eliminated`（脱落）、`timed_out`（時間切れ）、`passed`（パス）。クライアントは、この順に、アニメーションで見せる（[ui.md](ui.md) の 4.4）。

### 6.4 不正な入力への対処

- 受け取るメッセージには、サイズの上限（例: 4 KB）と、形式の検証を設ける。検証に通らないものは、破棄し、繰り返す接続は切る。
- 1 接続あたりの、メッセージの送信頻度に上限を設ける。
- ルール違反の操作は、`rejected` を返す。状態は、変えない。
- 接続を許すオリジン（ブラウザのページの出どころ）は、設定で決める。ローカルでは、ローカルホストだけ。

## 7. AI

AI は、サーバーの中で動く、席の 1 つ。人間の席と、同じルールで動く（特別な力はない）。

| 強さ | 動き方 |
| --- | --- |
| 1 | 合法な行動から、ほぼランダムに選ぶ。ただし、捕食できる行動があれば、優先する。引いた 4 枚からは、ランダム |
| 2 | 自分の 1 手だけ先を、評価関数で読んで、最もよい行動を選ぶ。引いた 4 枚からは、評価の高い駒 |
| 3 | 自分と相手の数手先（2〜3 手）まで探索する。持ち時間の中で、浅いほうから深くしていき（反復深化）、時間が来たら、そこまでの最善手を指す |

- **評価関数**（強さ 2・3 で共通）: 自分の城の HP、盤上の駒の価値（攻撃力・HP・大きさ）、持ち駒の価値、相手の城の HP、危険な駒の数（[game-rules.md](game-rules.md) の 8 章と同じ判定）を、重み付きで合計する。
- **時間**: AI の持ち時間は 20 秒（R-30）。探索は、安全のため、15 秒で打ち切る。残りは、通信と演出の余裕。
- **乱数**: ドローは、サーバーが決める。相手のドローの結果は、読めないので、強さ 3 では、相手が盤上の駒の移動だけを行うものとして読む。
- **強さ 3 の探索**:
  - 自分の行動を根として、最大 3 手先まで読む（自分と相手の手を、合わせて数える）。相手が複数のときは、全員が自分の評価を下げるように動くとして読む。アルファ・ベータ法で枝を刈る。
  - 相手（と、根より深い自分）の手は、捕食できる敵の駒の価値の高い順に、上位 10 手だけを読む。根の手は、すべて読む（配置が多すぎるときは、間引く）。
  - 反復深化: 深さ 1 の結果から始め、深さ 2、3 へ進める。締め切りを過ぎたら、途中の深さの結果は捨て、終えた最も深い結果で指す。前の深さの評価の高い手から読む。
  - 終局は、早い勝ちを好み、遅い負けを好む。
  - 締め切りは、呼び出し側（サーバー）が決めて渡す。
- **再現性**: AI の乱数も、ゲームのシードから決まる。同じシードと同じ状況から、同じ手になる。

## 8. 対局の記録（SQLite）

- 対局ごとに、次を保存する。**対局中の状態は、メモリを正とし、記録は、書き込み専用の履歴**（再起動後の復元は、対象外）。
  - ゲームの ID、ルール（設定の値）、乱数のシード、開始・終了の日時、結果（順位・終了理由）
  - 席（人間／AI、表示名、AI の強さ）
  - 手番ごとの記録: 手番番号、席、引いた 4 枚、選んだ駒、行動、出来事、かかった時間、時間切れか
- 記録から、シードと行動の列をもとに、対局を再現できる（[game-rules.md](game-rules.md) のルールは、決定論的に動く）。
- 個人を特定できる情報は、保存しない（表示名は、ゲストの名前）。

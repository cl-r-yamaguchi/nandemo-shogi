# Issue #3: 安全フックの強化（`fix/3-harden-block-hook`）

PR #2 マージ後、自動セキュリティレビューが `scripts/hooks/block-dangerous.sh` に 2 件を指摘した。どちらも妥当と判断して対応した。

## やったこと

- fail-open の解消: `jq` が無い場合と入力不正・処理失敗の場合に、終了コード 2 でブロックするようにした（`trap ... ERR` と `jq` の存在確認）。
- ブロック漏れの補完: コマンドを `; & |` で区切って片ごとに判定し、次を検知するようにした。
  - git のグローバルオプションを挟んだ push（例: `git -C dir push`）
  - `--force-with-lease`、`+refspec`、`-uf` のような短い形式の連結
  - rm の `-R`、`-r -f` の分割指定、`--recursive --force`
- `.claude/settings.json` の `deny` に、強制 push と再帰的な強制削除を追加した（フックとの二重防御）。
- コミット前の `/security-review` と `/code-review` の指摘を受けて、さらに次を直した。
  - `$(rm -rf x)` やバッククォート内、`/bin/rm`・`/usr/bin/git` のようなパス付き呼び出しを見逃していたため、コマンド名の直前の境界を「空白のみ」から「英数字・`_`・`.`・`-` 以外」に広げた。
  - `2>&1` の `&` で断片が分かれ、`--force` が切り離される問題を、リダイレクトを先に取り除いて解消した。
  - `$(git push --force)` のように `--force` の直後が `)` でも検知するようにした。
- 検証: 回避パターンがブロックされ、通常の push や `ls` などが通ること、`jq` なし・不正入力で終了コード 2 になることを確認した。
- 指摘のうち、`+` 始まりの引数や `-fix` のような値が誤ってブロックされる点は、強制 push の検知を優先して許容した。

## 判断とその理由

- 正規表現のブロックリストだけでは完全には防げないため、`deny` ルールとの併用にした。

## 未解決

- GitHub 側の `main` のブランチ保護（強制 push 禁止）は未設定。リポジトリ設定を変える操作なので、ユーザーに確認してから行う。
- コマンド文字列内の危険な文字列（`echo` の引数など）を実行しなくても検知する挙動は、そのまま。
- 追加の自動セキュリティレビューで、クォート・バックスラッシュ・変数展開を挟む書き方（例: `r""m`）で回避できると指摘された。正規表現では原理的に塞げないため、Issue #6（`shlex` でトークン化）に切り出した。誤操作防止が目的で、`git push` は `ask` で人が確認するため、緊急度は低いと判断した。

# Issue #12: rules: 駒データ・盤・状態の基本型（`feature/12-rules-core-types`）

PR #11 マージ後に着手。`rules` の第 1 段として、駒データ、盤の幾何、状態の型と不変条件を実装する。

## やったこと

- `data/pieces.toml` に、駒 12 種の定義を書いた（数値の唯一の定義）。`docs/specs/pieces.md` は、数値を持たず、設計の意図とデータの書き方だけにした。
- `rules` に、駒データの読み込みと検証（`pieces.rs`）、盤の幾何（`geometry.rs`）、状態の型と不変条件の検証（`state.rs`）を実装した。テストは 40 件。各規則（R-01〜R-04、R-10、R-53）と、駒ごとの移動量の数を確認している。

## 判断とその理由

- 駒の数値を `pieces.toml` だけに置いた。仕様書との二重管理を避けるため（設計の原則 4）。
- 駒データの読み込み時に、不正なデータ（重複 id、存在しない成り先、不正な大きさ・HP・移動範囲、城なし）を拒否する。実行時の不具合を、起動時の検証で防ぐため。
- `/code-review` の指摘を反映した。駒データの検証を強め（未知のキー、巨大な値、城の条件、成りの連鎖）、状態の検証に、手番・持ち駒・駒の番号の検査を足した。人数・盤の大きさは設定値として渡せる。
- 状態の `validate` は、最初に見つけた違反を返す（全件の列挙はしない）。ルールの適用後の検証に使うため、速さを優先した。

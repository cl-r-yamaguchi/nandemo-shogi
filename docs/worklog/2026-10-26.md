# Issue #14: rules: 行動の適用（`feature/14-rules-actions`）

## やったこと

- `rules` に、行動の適用（`action.rs`）を実装した。`apply` は、元の状態を変えず、新しい状態と出来事の列を返す。

## やったこと

  - `turn.rs`: ドロー `draw_cards`（R-05）と、時間切れ `time_out`（R-14・R-31）。

- 時間切れの強制パスは、行える行動があっても行う（R-31）。
- 終局したら、手番の段階を `Act` に戻す。手番数の上限や投了で終局したときに、ドロー待ち・選択待ちが残る不具合を、テストで見つけて直した。

## 未解決・次にやること

# Issue #20: rules: 危険な駒の判定（`feature/20-rules-threats`）

PR #19 マージ後に着手。次の一手で捕食されうる駒の判定を `rules` に実装する。

## やったこと

- `rules` に、危険な駒（次の一手で捕食されうる駒）の判定を実装した（`threats.rs`）。
  - `threats`: 捕食されうる駒ごとに、その駒を捕食できる攻撃側の駒の一覧を返す。`threatened_pieces`: 「！マーク」を付ける駒の集合。
  - 攻撃のダメージ計算を、`action.rs` の `strike_damage` に切り出し、移動の適用（`apply`）と判定が同じ計算を使うようにした。
- 仕様を `game-rules.md` の 8 章（R-A0〜R-A2）に足し、`ui.md`・`online.md` の参照を直した。
- テストは 168 件（判定で 14 件）。ランダムに駒を撒いた盤 40 通りで、判定が `apply` の実際の捕食と一致することを確認している。

## 判断とその理由

- 攻撃側は「持ち主以外の、脱落していないプレイヤー」の駒すべてにした。手番の順は見ない。画面は、誰の駒でも、狙われているかが分かればよいため。
- 同じ持ち主の駒は、危険の原因にしない。味方を捕食できても、それは自分の意思の行動であり、「とられる」危険ではないため。
- 判定は、ダメージ計算を実際の攻撃と共通化したうえで、`apply` との一致を、ランダムな盤で確かめるテストで保証する（片方だけが変わっても、気づける）。

## 未解決・次にやること

- `rules` は、これで完成。次は、`ai`（強さ 1 → 2 → 3）。
- 性能: 判定は、全駒 × 全移動先 × 全駒の走査。AI の探索で多用するときは、計測して、必要なら最適化する。
- `/code-review` の指摘を反映した。脱落したプレイヤーの駒は、守られる側としても数えない。攻撃が、攻撃側の味方の駒にも重なる場合（味方が生き残って移動は取り消されるが、敵へのダメージは先に入る）を、テストで固定した。`ui.md` の変更履歴に、危険マークの定義の変更を記録した。

## やったこと

  - 相手の手は、盤上の駒の移動だけ。捕食できる敵の駒の価値の高い順に、上位 10 手を読む。
  - 反復深化: 深さ 1（強さ 2 の評価）から始め、深さ 2、3 へ。締め切りを過ぎたら、途中の深さの結果は捨て、終えた最も深い結果で指す。前の深さの評価の高い手から読む。
  - 終局は、早い勝ちを好み、遅い負けを好む。
- `rules` の `strike_damage` を公開した（ダメージ計算を、`apply`・危険判定・AI の手の並べ替えで共通にするため）。

## 判断とその理由

- 根の手の探索窓は、最善より少しだけ低い値を下限にした。同点の手も正確な値を得て、ランダムに選べるようにするため（同点を枝刈りで落とさない）。
- 途中までしか終えていない深さの結果は捨てる。浅い深さの完全な比較のほうが、深い深さの一部だけの比較より、信頼できるため。
- 相手のドローは読まない。乱数で決まる、かつ、読むと枝が爆発するため。

# Issue #26: protocol: メッセージの型と検証（`feature/26-protocol`）

PR #25 マージ後に着手。クライアント・サーバー間のメッセージの型と、受信の検証を `protocol` に実装する。

## やったこと

- `protocol` に、メッセージの型（`ClientMessage`・`ServerMessage`、版つきの `ClientFrame`・`ServerFrame`）、盤面の写し（`StateView`）、受信の検証（`decode_client`）を実装した。TypeScript の型は、`cargo test -p protocol` で `web/src/net/generated/` に生成する。
- `rules` に、JSON 化（`serde`）と、TypeScript の型の生成（機能 `ts`、既定ではオフ）を足した。`rules-wasm` は、機能 `ts` を使わない。
- `web/src/net/index.ts` を、生成した型の窓口にした。型が使えることを、TypeScript のテストで確認している。
- `online.md` の 6 章を、実装に合わせて更新した。
- テストは `protocol` 31 件、`web` 5 件。

## 判断とその理由

- 選択（`pick`）は、独立のメッセージにせず、`act` の行動の 1 つに統合した。`rules` の `Action` に `Pick` があり、同じ検証・手番番号の仕組みに乗せられるため。
- `rules` の型を、そのままメッセージに使う。`protocol` で同じ型を作り直すと、ルールの変更のたびに 2 か所を直すことになるため（設計の原則 4）。
- `StateView` は、`GameState` を直接 JSON にせず、写しを作る。駒の番号の発行などの内部を漏らさず、手元の駒を一覧にして、TypeScript で扱いやすくするため。
- 駒の種類は、番号（`data/pieces.toml` の並びの順）で送る。サーバーとクライアントが、同じデータを埋め込むので、通信を短く保てる。駒を追加・並べ替えたら、クライアントとサーバーを同時に更新する（版は、メッセージの形が変わったときに上げる）。
- 版を先に読む。未知のメッセージでも、版違いを、版違いとして返せるため。
- `rejected` は、`code`（単純な文字列）と、`reason`（不正な行動のときだけ）に分けた。クライアントが、`code` だけで分岐できるため。

## 未解決・次にやること

- ルーム・マッチング・タイマー・切断の処理（次の Issue）。WebSocket の通信と、SQLite への記録は、その次。
- 送信頻度の上限、オリジンの検証は、通信の実装（WebSocket）で行う。
- `/code-review` の指摘を反映した。
  - 版を、1 回のパースで、数値として読む（範囲外・小数の版も、版違いとして返す）。
  - 表示名に、ゼロ幅の文字・向きを変える文字・BOM など、見えない文字を使えないようにした（なりすまし対策）。
  - TypeScript 側の `PROTOCOL_VERSION` が、Rust 側と一致することを、テストで固定した。
  - 拒否の文言を、上限の定数から作る。
  - 配置フェーズの手番番号を、城を置いた数に決めた（`rules` の `turn` が、配置フェーズでも進み、対戦フェーズが始まると 0 に戻る）。`act` の `turn` で、二重送信を見分けられる。仕様書（`spec.md`・`online.md`）も更新した。
  - `protocol` の TypeScript 生成を、機能 `ts`（既定で有効）にした。サーバーは、`default-features = false` で外せる。
  - 盤上の駒は、`rules` の `Piece` を直接使わず、`PieceView` にした。`rules` の内部が、通信の形に漏れない。`Piece` の JSON 化の指定は、外した。
- 見送り: `RoomRules` の値が、`u8` の範囲外のときは、`invalid_rules` ではなく `bad_message` になる。どちらも拒否なので、現状のまま。

# Issue #28: server: ルーム・マッチング・手番の進行（`feature/28-server-rooms`）

## やったこと

- `server` を、ライブラリ（`lib.rs`）と実行ファイルの両方にし、通信に依存しない、ルームとマッチングを実装した。`protocol` は、TypeScript 生成なしで依存する。
  - `room.rs`: 待機（入室・退室・Go・満員で自動開始）、席順（人間と AI を交互に。最初の手番はランダム）、対局の進行（ドロー・手番番号の照合・行動の適用・出来事の配信・終局）、AI の手番、時間切れ、切断と AI の代行、再接続、投了、期限（待機 10 分、全員切断 60 秒）。
  - `lobby.rs`: マッチング（同じルールの、待機中で空きのある、最も古いルーム。なければ作る）、プレイヤーとルームの対応、終わったルームの片付け、AI の手番の駆動。
  - `outbound.rs`: 送るべきメッセージ（宛先のプレイヤー ID と `ServerMessage`）。
- `protocol` の `RejectCode` に、`not_waiting`・`room_full`・`already_in_room` を足した。
- テストは `server` 63 件（時計を進めるテスト、人間 1 人 + AI の対局を終局まで、同じシードで同じ対局、など）。

## 判断とその理由

- ルームは、時計（`Millis`）と乱数を、呼び出し側から受け取り、送るメッセージを返す形にした。通信なしで、時間の経過（持ち時間、切断、期限）を、テストで再現できる。実際の時計と通信は、次の Issue の層が担う。
- ドローは、サーバーが手番の開始で自動で行う（クライアントは、ドローを要求しない）。ドローで引いた駒は、出来事として全員に送る。
- ドローと時間切れの乱数（`draw_rng`）と、AI の乱数（`ai_rng`）を、同じシードから分けた。AI の考え方が、ドローの結果に影響しないようにするため。
- 選択（`pick`）と、手番でない人の投了は、次の手番を始めない（`Step.new_turn`）。
- 配置フェーズで、城を置けないまま時間切れになったときは、投了扱いにする。置けないまま手番を進めると、配置フェーズが終わらなくなるため。
- 終わったルームは、結果を送ったあと、`tick` と `sweep` で片付ける。同じプレイヤーが、そのまま探し直せる。

- `/code-review` の指摘を反映した。
  - AI の手番を、計画（`plan_ai`、状態の写し）・考える（`AiPlan::think`、ルームに触れない）・反映（`apply_ai`、考え終わった時刻を渡す）に分けた。考えている間、ロビーを止めない。次の人間の持ち時間は、考え終わった時刻から数える。考えている間に状態が変わっていたら、結果は捨てる。`run_ai` は、3 つをまとめた、テスト向けの入口。
  - 待機中の投了で、プレイヤーとルームの対応が残る問題を直した。AI が手を返せなかったとき、手番を強制的に終える。投了できないとき（すでに脱落）は、エラーを返す。「全員が切断してから 60 秒」の起点を、最後の切断の時刻にした。手番の開始で、ドローしたときだけ盤面の写しを作る。
  - 「すでにルームに入っています」の案内を、対戦中の場合を含めて書き直した（対戦中の退室は、仕様どおり、切断として扱う）。

# Issue #30: server: WebSocket の通信（`feature/30-server-websocket`）

PR #29 マージ後に着手。axum で WebSocket の入口を作り、ロビーへ振り分ける。

## やったこと

- `server` に、WebSocket の通信を実装した。
  - `ws.rs`: axum の入口（`/ws`）。オリジンの検証（許可に含まれない、またはない接続は 403）、同時接続数の上限（503）、通信の層でのメッセージの大きさの上限、最初の `hello` の待ち時間（10 秒）、テキストのみ、検証（`decode_client`）、拒否の返信。
  - `hub.rs`: 接続の管理（プレイヤー ID ごとに 1 接続。新しい接続が古い接続を置き換える）、ロビーへの振り分け、結果の配送（詰まった遅い接続は切る）、時計の駆動（250 ミリ秒ごとの `tick`）、AI の駆動（計画 → 別スレッドで考える → 最低 1.5 秒の間を置いて反映。同じルームで重ならない）。
  - `rate.rs`: 送信頻度の制限（トークンバケット: 一度に 30 件、毎秒 10 件）と、不正が続いたときの打ち切り（8 回）。
  - `main.rs`: 設定を読み込んで待ち受ける。接続・対局の開始と終了・拒否をログに出す（プレイヤー ID・表示名は出さない）。
  - `config.rs`: 同時接続数（`NANDEMO_MAX_CONNECTIONS`）と AI の間（`NANDEMO_AI_DELAY_MS`）を追加。
- テストは `server` 109 件（頻度の制限、オリジンの照合、接続を模した窓口でのハブ、本物の WebSocket を通した通し: オリジン・503・`hello`・不正な入力・頻度超過・対局の開始・城の配置・再接続・置き換え）。
- 実行ファイルを起動して、`curl` で、許可されたオリジンは 101、許可されないオリジンは 403 になることを確認した。
- `CLAUDE.md`・`architecture.md`・`online.md` を更新した。

## 判断とその理由

- ハブは、通信の形（WebSocket）に依存しない。接続は、送信口（`mpsc`）を持つ窓口として扱う。通信なしで、振り分け・配送・置き換え・遅い接続の切り離しを、テストできる。
- ロックは、短く持つ（メッセージごとに完結）。AI が考える間は、ロビーのロックを手放す（計画 → `spawn_blocking` → 反映）。
- 接続の送信口は、大きさに上限を設けた有限の送信口。読まない遅い接続が、メモリを食い続けないようにするため。詰まったら、その接続を切り、ロビーに切断を知らせる。
- 古い接続からのメッセージは、無視する（接続の番号で照合）。置き換えられた古い接続が閉じても、新しい接続の切断にならない。
- `Origin` がない接続も拒否する。ブラウザは、WebSocket の接続に、必ず `Origin` を付けるため。ブラウザ以外のクライアントが `Origin` を偽ることは防げないが、ローカル限定・認証なしの前提では、ブラウザ経由の、別のサイトからの接続（クロスサイトの乗っ取り）を防ぐことが目的。
- プレイヤー ID は、ほかのプレイヤーに送るメッセージ（席・通知）に含めない。ID を知っている人だけが、その席に戻れる。

## 未解決・次にやること

- SQLite への対局の記録（次の Issue）。
- 既知の制約: `hello` のあと、何も送らない接続は、閉じない（同時接続数の枠を使い続ける）。ローカル限定なので許容するが、外部公開するときは、無通信の期限を足す。
- 外部公開には、認証・接続元ごとの制限が、別途必要（対象外）。

## レビュー（`/code-review`）の反映

- 詰まった接続や、置き換えられた古い接続が、実際には閉じられない問題を直した。接続ごとの「閉じる合図」（`Notify`）をハブが持ち、読み込みの側が、それを待つ。送信口を手放すだけでは、読み込みの側が閉じないため。
- Ctrl-C で、接続が残っていると終了が待たされる問題を直した。`Hub::shutdown` が、全接続に合図を送ってから、サーバーが終わる。
- `hello` を送らない通信路が、接続数の上限に数えられない問題を直した。通信路を開く時点で数える（`try_open_socket`、手放すと減る）。
- 無通信・半開きの接続が残る問題を直した。30 秒ごとに ping を送り、何も届かないまま 90 秒たったら閉じる。通信の層で拒否された大きすぎるフレームにも、理由（`too_large`）を返す。
- 頻度超過に、サイズ超過の `too_large` を使っていたので、専用の `rate_limited` を足した（TypeScript の型も再生成）。
- AI の思考が異常終了したときは、手番を強制的に終える（同じ失敗を、250 ミリ秒ごとに繰り返さない）。配送を 8 周で打ち切って、メッセージを捨てる問題を直した（1 周ごとに必ず接続が減るので、尽きるまで続けても終わる）。`NANDEMO_MAX_CONNECTIONS=0` を拒否する。
- プレイヤー ID が、秘密であることを、`online.md` に明記した（認証は対象外）。

# Issue #32: server: SQLite への対局の記録（`feature/32-server-sqlite`）

PR #31 マージ後に着手。終わった対局を SQLite に保存し、記録から再現できるようにする。

## やったこと

- `record`（新規・純粋）: `GameRecord`（ルール・シード・席・操作の列・結果）と、`replay`。最初の手番をシードから決め、操作を順に適用し直して、記録された出来事・結果と一致することを確かめる。席の数・手番番号・席が合わないもの、出来事・結果が違うものは、エラーにする。
- `room`: 履歴の 1 件を、`Move`（`Draw`・`Act`・`TimeOut`・`Resign`）で表すように変えた（以前は、`action: None` が、ドローと投了で区別できなかった）。`Room::record()` を追加。
- `lobby`: 終わったルームを片付けるとき（`sweep`）、記録の渡し先（`RecordSink`）に渡す。対戦が始まらなかったルームは、記録しない。
- `store`（新規）: `Store`（開く・保存・読み出し・件数）と、専用スレッドで保存する `StoreWriter`。`main` が、起動時に開き（開けなければ起動しない）、Ctrl-C のときは、頼まれた分を保存してから終わる。
- 依存: `rusqlite`（SQLite を同梱）、`serde`（`server` でも使うため）。

## 判断とその理由

- 保存は、専用スレッド（`std::thread` と `mpsc`）。ロビーのロックを持ったまま、ディスクに書かないため。`Lobby` は、保存の関数を受け取るだけで、DB を知らない。
- 保存は、失敗しても、対局に影響させない。標準エラーに出すだけ（記録は、書き込み専用の履歴で、メモリが正）。
- シードは、`u64` を欠けなく残すため、文字列で保存する（SQLite の整数は、符号つき 64 ビット）。
- プレイヤー ID は、保存しない（本人だけが知る合言葉のため）。テストで、DB のどの列にも入っていないことを確かめた。
- 時間切れ・投了の席は、操作に記録する。ドローと時間切れは、同じ乱数（`draw_rng`）を使うので、操作の順番どおりに適用し直さないと、再現できない。
- 「かかった時間」は、記録しない（仕様から外した）。再現に必要なのは、操作の順番だけで、時計は、対局の結果に影響しないため。

## 未解決・次にやること

- 既知の制約: サーバーを止めたとき、進行中の対局は、記録されない（メモリだけにある）。
- 記録の閲覧用の画面・API、古い記録の削除は、対象外。
- 次は、フロントエンド（`rules-wasm` と `web`）。

## レビュー（`/code-review`）の反映

- 異常終了のときも、頼まれた保存を終えてから終わるようにした。スキーマの版は、新規のファイル（版 0）にだけ付ける。
- 対応しないもの: 終了時に進行中の対局を「中断」として記録すること（既知の制約として上に記載）、保存の待ち行列の上限（ローカル用途で、保存は軽い）、保存の関数がロックの中で呼ばれること（送信口に送るだけ）。

## セキュリティレビュー（`/security-review`）

- 確度の高い指摘なし。SQL はすべてパラメータ化、DB のパスは環境変数のみ、プレイヤー ID は記録にも DB にも入らないことを確認した。


# Issue #34: rules-wasm: 盤面の問い合わせ（`feature/34-rules-wasm-queries`）

PR #33 マージ後に着手。フロントエンドが、ルールと同じ計算（移動範囲・配置先・プレビュー・危険判定）を呼べるようにする。

## やったこと

- `rules`: `GameState::restore(StateParts)` を追加（盤面の写しから復元。次の駒の番号は、最大の番号 + 1。脱落の順は、脱落した席を 1 人ずつの組で補う近似）。
- `protocol`: `StateView::to_state`（復元して、不変条件を検査する）。
- `rules-wasm`: `piece_kinds`・`legal_actions`・`legal_targets`・`legal_placements`・`preview`・`threatened`。本体は `queries`（wasm に依存しない。文字列 → 文字列）で、wasm の窓口はそれを包むだけ。カタログは、1 度だけ読み込む。
- `web/src/rules-bridge`: 型つきの窓口（`Rules`）。`loadRules` は、バイト列を直接渡せる（テスト用）。TypeScript のテストを追加し、`@types/node` を足した。

## 判断とその理由

- 状態を持たない（毎回、写しから復元）。クライアントの状態の持ち主は `store` で、wasm 側に二重に持たないため。復元は、駒の数に比例する軽い処理。
- 不正な入力は、例外にする。盤の大きさは 64 まで（全マスを調べる問い合わせの、無駄な重さを避ける）。
- テストは、wasm の関数の結果が、`rules` の直接の呼び出しと一致することを確かめる形にした（ルールを二重に書かない）。

## 未解決・次にやること

- 脱落を伴う行動のプレビューでは、順位は近似。画面は、サーバーが送る結果を正とする。
- 次: クライアントの `net`（WebSocket）と `store`。

## レビュー（`/code-review`）の反映

- `GameState::restore` が、検査（`validate`）まで行い、`Result` を返すようにした（検査されない状態を作れない）。駒の番号の桁あふれ（最大値 + 1）は飽和で扱い、プレイヤー数が 255 を超える写しは拒否する。
- 写しの持ち駒の表で、同じ種類が重なる・個数が 0 のものを拒否する（`Violation::MalformedHand`）。
- Node の型は、共有の `tsconfig` から外し、テストのファイルだけが参照する。`npm test` の前に wasm をビルドする（`pretest`）。ブリッジの余計な `try/catch` を外した。
- 対応しないもの: 問い合わせごとに写しを文字列にして復元する費用（実測してから最適化する）。

## セキュリティレビュー（`/security-review`）の反映

- 盤の内側の検査（`Rect::is_inside`）が、座標が `i32` の端のとき、あふれて、盤の外の駒が検査を通る（リリースのビルドでは、あふれが回り込む）問題を直した。広い型で比べる。テストを追加。ほかの確認（持ち駒・プレイヤー数・駒の番号・盤の大きさ・コード実行）は、問題なし。
